# Hyperliquid Pair 止盈止损监控、人工平仓与自动化规划

日期：2026-11-11。

状态：只读监控、触发提醒和人工确认平仓已在 `87ffcd8` 实现；全自动执行尚未实施。本文不授权真实交易或自动下单。当前监控使用两腿未实现盈亏之和，触发后由用户通过现有目标为 0 的调仓弹窗重新预览、签名并确认，后台 worker 不持有交易私钥也不发送订单。以下第 3–4 节同时包含未来自动执行的设计要求，不能据此认为当前已具备自动执行、完整策略净盈亏或保证全部平仓能力；实际部署版本见[项目状态](PROJECT_STATUS.md)。

## 1. 为什么不能只使用交易所原生止盈止损

Hyperliquid 原生止盈止损作用于单个合约，不知道另一腿的仓位，也无法按 pair 整体盈亏触发。例如 NBIS 盈利 `+800 USD`、CRWV 亏损 `-500 USD` 时，pair 整体盈利为 `+300 USD`；单腿订单无法根据这个合计值同时关闭两腿。

如果只让其中一腿触发原生止盈止损，另一腿可能仍然持仓，使原本对冲的 pair 变成单边裸仓。因此需要独立的 **pair 级风险管理和执行功能**。

原生单腿止盈止损仍可保留为灾难保护，用于降低 hl-trader 后端不可用时的风险，但它不能替代 pair 级规则。系统必须识别原生订单导致的仓位变化，并明确提示另一腿可能已经裸露，不能把单腿成交视为整个 pair 已完成平仓。

## 2. Pair 整体盈亏口径

第一版使用当前两腿未实现盈亏之和：

```text
pair_unrealized_pnl = leg_1_unrealized_pnl + leg_2_unrealized_pnl
```

止盈和止损分别以 USD 金额配置。例如整体浮盈达到 `take_profit_usd` 或整体浮亏达到 `stop_loss_usd` 时触发。两腿任一数据缺失、过期或身份不一致时不得使用残余旧值计算并触发。

后续可增加策略累计净盈亏口径：

```text
strategy_net_pnl = current_unrealized_pnl
                 + realized_pnl_since_activation
                 + funding_since_activation
                 - fees_since_activation
```

该口径需要明确策略启用基线，并完整核算减仓、加仓、资金费和手续费。不能把当前浮动盈亏与策略启用以来的累计净盈亏混为一谈。第一版不包含移动止损、复杂分批止盈或跨 pair 合并盈亏。

## 3. 运行方式与配置

自动化必须由后端持久 worker 执行，不能依赖浏览器页面保持打开。每个 `pair + account` 独立配置和隔离，至少包含：

- 是否启用；默认关闭，启用自动执行必须另行明确确认。
- 止盈金额、止损金额和盈亏口径。
- 触发后的平仓比例；第一版固定为两腿 `100%` 平仓。
- 行情和仓位允许的最大数据年龄。
- 最大允许滑点、执行期限和告警方式。

监控、触发与执行记录按 pair、账户和配置版本关联。修改账户、仓位或规则后不能沿用旧配置的触发结果。

## 4. 触发与执行安全

触发后复用现有目标仓位调整能力，将两腿目标设为 `0`，使用 reduce-only 订单关闭实际仓位。执行前重新读取最新仓位、挂单和盘口，并取得该 pair + 账户的执行锁，防止网页手工调仓、其他 worker 和止盈止损并发写入。

当前已实现的监控与人工执行状态为：

```text
disabled / monitoring / triggered / executing / completed / incomplete / unknown / unavailable
```

当前触发写入规则和事件；request ID / 动作 ID 来自用户后续选择的调仓执行链路，不能把提醒当成已生成订单。未来自动执行必须在发送前持久化执行身份，worker 重启后先核对原动作，不重复生成新订单。

- 两腿目标为 0 仍需逐腿通过最小名义与精度校验。`9e3ad44` 会跳过保护价名义不足 10 USD 的腿，可能留下残仓；执行完成不能直接等同于两腿实际均为零，需核对最终仓位。
- 两腿不是原子交易。拒单、部分成交、超时或断线时必须保存每腿已确认的成交和剩余仓位。
- 明确失败时停止后续未经核对的写操作；结果未知时先按 request ID、action ID、cloid、订单和实际持仓核对，禁止盲目重试或反向补偿。
- IOC 保护价只限制可接受价格，不保证全部成交。未完全平仓必须进入明确的未完成状态并告警。
- 原生单腿订单、手工调仓或其他外部仓位变化会使原执行前提失效，必须重新核对，不得继续按旧数量下单。
- pair 止盈止损不是强平保护或保证亏损上限；流动性、跳空、部分成交和系统不可用风险仍由交易者承担。

## 5. 分阶段实施

1. **只读监控与预览（已实现）**：展示 pair 当前整体盈亏、止盈止损距离和预计平仓结果，不发送订单。
2. **提醒与人工确认（已实现）**：达到条件后告警，由用户在页面核对最新盘口并一键确认关闭两腿。托管、浏览器本地和扩展钱包均沿用现有调仓执行链路，结果回写规则状态和事件记录。
3. **全自动执行（未实现）**：未来仅为显式启用的 pair + 账户开放，接入自动执行 worker、执行锁、幂等恢复、告警和完整回执。

当前规则、状态和事件存于 migration `010_pair_risk_controls.sql`，按登录用户、pair 和账户隔离。worker 通过 `--kind pair_risk` 或常驻 scheduler 运行；`HL_APP_RISK_MONITOR_ENABLED` 是任务开关，默认间隔 30 秒，快照超过 30 秒不使用，页面最后尝试超过 60 秒会显示监控不可用。该开关与股票采集开关独立，规则默认关闭，至少配置一个正数止盈或止损金额才能启用。

每一阶段先使用 fixture、mock、临时数据库和离线状态机测试。真实主网自动下单、启用常驻自动执行 worker 和部署重启均需用户另行明确授权；当前常驻 worker 仅做只读监控。

## 6. 后续验收重点

- 两腿盈亏合计、阈值方向、资金费和手续费口径符合所选模式。
- 数据过期、单腿缺失、跨账户或跨配置串数据不会触发订单。
- 浏览器关闭后监控仍按明确的 worker 配置运行；worker 停止时页面明确显示自动化不可用。
- 重复触发、并发调仓、进程重启、拒单、零成交、部分成交和超时不会造成重复下单或反向开仓。
- 一腿已经由交易所原生订单关闭时，系统能识别并处理另一腿裸露风险。
- 页面可查看规则、最近触发、每腿订单、成交结果和最终仓位；未执行的真实能力不得显示为已上线。

## 3. 修复批次 A：Rust 数据正确性（R1、R3、R6、R7、R8）

主要修改 `src/dashboard/snapshot.rs`，必要时调整只读 client 的数据表示。保持现有交易模块不动。

### A1. 一次调整行情字段和上市状态模型（R1 + R8）

`AssetCtx` 的 `funding`、`mark_px`、`oracle_px` 改为可缺失值；解析失败不能统一补零。上市状态区分“无元数据”“存在且活跃”“明确下架”，不能仅用 universe 中找到名称作为正常上市依据。

- 字段缺失/null/非法字符串：对应字段不可用并附诊断，保留其他有效字段。
- 合法 `funding="0"`：这是已知零费率，允许计算，不能用真假值判断丢弃。
- mark/oracle 缺失或非正：相应名义/估算不可计算，数量与交易所盈亏保留。
- 有持仓腿的 funding 或 oracle 不可用：组合 daily_estimate=null。未持仓腿的费率缺失不影响另一条有效持仓的可计算估算。
- `isDelisted=true`：明确诊断且行情区块不能为 ok；不再作为正常活跃行情提供实时比价/估算。已有实际仓位继续展示，不把下架等同于账户空仓。
- 只有使用失败字段的读数降级，实际资金费历史不受当前费率缺失影响。

必须测试：缺字段、null、非法数字、合法零费率、负费率、无持仓腿缺费率；合约不在 metadata 和 `isDelisted=true` 分别覆盖。

### A2. 区分资金费查询结果（R3）

在 history 到 funding block 的转换中明确三种情形：

| 情形 | actual_48h_net | recent_payments | window_complete |
|---|---|---|---|
| 完整成功，窗口内没有该 pair 记录 | `"0"` | `[]` | true |
| 不完整，且没有有效的该 pair 记录 | null | null | false |
| 不完整，已有有效的该 pair 记录 | 已获得部分合计 | 已获得最近记录 | false |

首请求失败不能因 `FundingHistory` 外层为 Some 就当成功处理。部分查询仅获得其他币种记录，也不能为当前 pair 显示已确认零收付。部分有效记录相抵为零时允许显示部分合计 0，但仍标不完整。

必须测试：首请求失败、第一页成功后失败、只有其他币种记录、完整空窗口、已平仓历史保留及部分记录相抵为零。

### A3. 修复单腿盈亏合计（R6）

仅在完整仓位集合查询成功后，对指定两腿的实际持仓行求和：单腿采用该行有效盈亏，双腿相加，确认空仓为 0。某个实际持仓行的盈亏未知时，合计为 null；不能把未知补 0。

必须测试：第一腿独有、第二腿独有、多/空及正/负盈亏；单腿示例 37.5 必须同时出现在行级数据与合计中。

## 4. 修复批次 B：Python 校验与失败处理（R4、R5、R9）

### B1. 完整降级 DTO 与语义校验一起修复（R4 + R9）

将 `_unavailable_block` 改为按 block 类型构造完整 DTO：数据字段齐全、未知数值 null、实际仓位 unknown/items=null、资金费两币 map 值为 null、比价 points=null；解锁 anchors=[] 并标 unavailable。固定 source keys 不能丢失。

降级字段不能保留未验证的原始值。资金费窗口只使用本次已知且合法的请求上下文；不得保留反向窗口，或把未知收付补成零。`unlocks_enabled=false` 始终输出 unlocks=null，不能用一个真值错误对象替代“不适用”。

补全校验：

- 每块必需字段与容许的 null；sources 固定 key、查询状态和时间；diagnostics 必须为字符串数组，ok 不含失败诊断。
- 资金费 start < end，差值恰好 48 小时；明细时间属于半开窗口 `[start,end)`，最多三条且倒序。
- window_complete=false 不能配 status=ok；完全未知历史不能伪装完整的 0/[]。
- 合约归属、数值有限性、数量/名义非负；明确区分 JSON 类型，避免 bool 作为整数接受。
- 列表/映射类型先检查再遍历，不能把空对象当作合法空列表。

错误区块单独降级，已验证有效的其他区块保留；整体身份/版本错误仍拒绝整份快照，不进入缓存。

前端同步保护：先依据 block 状态及已验证字段渲染，特别是 unlocks 不可用时不执行未检查的 `anchors.length`，也不显示“未来没有事件”的正常空态。

必须测试：删除/损坏每种 block 字段，检查输出完整形状；损坏 anchors 的快照经后端校验后进入详情页，页面不崩溃且其他块保留；反向/非 48 小时窗口、越界明细、重复/错误来源键、对象类型错误、不完整却 ok 均被拒绝或降级。

### B2. 使用真正非阻塞的双管道读取（R5）

在 v1/v2 共享的 `_communicate_bounded` 中：

- Popen 使用二进制 stdout/stderr，设置文件描述符非阻塞；selector 就绪后使用有界 `os.read`，不要对 TextIOWrapper 执行定长 `.read(65536)`。
- 同时排空 stdout/stderr，按字节累计限额；UTF-8 在完整有界字节收集后处理，不能分块误切中文字符。
- 整体期限使用 monotonic；读取、等待退出使用同一个 deadline，不能输出 EOF 后额外无条件再等数秒。
- 超时、超限、读取异常都终止并回收子进程，关闭管道/selector，释放采集并发许可。
- 对外仍是安全错误文本，不返回 stderr、路径或 traceback。

必须测试真实的临时 Python 子进程：少量输出 flush 后 sleep、完全无输出、双管道交替压力、超过上限、关闭输出后不退出、分块多字节字符。使用合理时间容差断言及时返回，并确认子进程已经结束。只 mock helper 返回值不能证明期限有效。

## 5. 修复批次 C：前端快照身份与刷新（R2）

修改总览和详情，移除跨 query key 的无条件 `keepPreviousData`。同一 key 的 refetch 本身可以保留缓存，不需要把其他 key 的数据作为 placeholder。

- 共用一个快照身份检查函数，比较 `config_revision`、pair ID、network、dex、有序 coins、归一化地址；不只检查地址相等。
- 在身份检查通过前，不渲染仓位、资金费、曲线或快照查询时间。总览卡片和详情都使用这个检查。
- query key 继续包含 revision 和 pair ID；配置变更后新 key 未加载时显示加载状态，不显示旧账户数据。
- 手动刷新先等待目录刷新成功，再按新目录身份刷新快照；目录失败时明确提示，保留内容只能以旧身份和旧时间展示，不能换新标题后沿用旧读数。
- 响应 revision 与当前目录不匹配时，刷新目录并受控重试；不要无限循环，持续不匹配应明确报错。
- 关闭本模块的窗口聚焦自动刷新，保持方案约定的手动刷新语义。

必须测试实际 QueryObserver/页面行为：同地址切 pair、两组地址都 null、同 ID 换账户、网络或合约顺序变更、慢请求迟到、刷新失败。同 pair 同 revision 刷新允许保留旧值并标时间；跨身份不能。页面层需覆盖标题和数据是否同时切换，不能只测试比较函数返回值。

前端尚无成熟测试入口时，优先复用现有工具做最小测试；不能以“当前没有测试框架”为由省略交互验收。保留可重复的测试命令和截图，构建成功不能证明 R2 修复。

# Hyperliquid 调仓盘口轮询与成交滑点实施合同

日期：2026-11-10。

状态（2026-11-19 更新）：新增有界滑点与整笔订单深度检查，当前实现见第 7 节；第 1–6 节保留历次合同。第 7 节已部署，真实盘口只读预览通过；没有进行真实下单验收，详见[部署记录](deployment/ADJUSTMENT_DEPTH_2026_11_19.md)。

## 1. 本轮范围

本轮只增加调仓弹窗的只读盘口展示和成交滑点展示：

- 弹窗打开且页面可见时，每 5 秒读取两腿 BBO；关闭弹窗或开始签名/执行后停止轮询。
- 调仓结果和交易历史显示成交均价、相对预览中间价的滑点百分比及滑点金额。
- 保持现有顺序执行、逐腿签名、IOC 保护价和失败后停止后续写入的语义，不改成批量下单。
- 本轮不把弹窗轮询与逐腿发送前刷新 BBO 混为一谈；后者及浏览器逐腿重签仍属独立变更。

实时价格只用于展示和提示旧预览过期，不自动修改已预览、已签名或已落盘的订单。

## 2. 只读盘口契约

新增 Web 入口：

```text
GET /api/v1/hyperliquid/pairs/{pair_id}/adjustment-quote?config_revision=<sha256>
```

后端校验当前 pair 和 revision，调用固定参数的 Rust `adjust-quote --json` 子命令。该命令只读取受控 pair JSON 和官方 `/info` BBO，不加载私钥、不获取写锁、不读取调仓回执，也不发送写请求。

返回 `{data: ...}`，其中数据字段为：

```text
schema_version = 1
pair_id
network
config_revision
queried_at
legs = [
  { coin, bid, ask, mid, book_time },
  { coin, bid, ask, mid, book_time }
]
```

价格使用十进制字符串。缺失、非法或非正价格、配置变化、进程失败均返回错误，不补 0、不返回伪造盘口。

后端按 pair＋revision 做 1 秒成功结果缓存和同 key 单飞，最多两个盘口子进程并发；失败不缓存。页面 API 仍只返回后端结果，不让浏览器直接访问交易所。

## 3. 弹窗状态与过期预览

弹窗独立展示两腿 bid/ask/mid 和盘口时间。轮询失败显示错误；已有旧数据时必须保留其原始时间，不能改写成当前时间。

当最新成功盘口与预览 `mid_px` 不同时：

- 显示“盘口已变化，请重新预览”。
- 禁用托管执行和浏览器签名按钮。
- 用户显式点击重新预览后才生成新报告；托管模式同时生成新的 `request_id`。
- 不用轮询结果覆盖当前报告、确认金额或签名状态。

盘口接口失败本身不伪造过期结论；已有有效预览仍按原安全流程处理。

## 4. 成交滑点口径

后端在确认成交后按已成交数量和预览 `mid_px` 计算，新增可空十进制字段：

- `slippage_pct`：百分比数值，例如 `0.25` 表示 0.25%。
- `slippage_usd`：按成交数量计算的滑点金额。

正值表示不利滑点，负值表示有利滑点：

```text
买入 slippage_pct = (avg_px - mid_px) / mid_px × 100
卖出 slippage_pct = (mid_px - avg_px) / mid_px × 100

买入 slippage_usd = confirmed_qty × (avg_px - mid_px)
卖出 slippage_usd = confirmed_qty × (mid_px - avg_px)
```

部分成交只按已成交部分计算；未成交或缺少有效均价时为 `null`，不补 0。历史报告没有这些字段时前端显示 `—`。

弹窗和交易历史继续分别展示预览中间价、IOC 保护价和实际成交均价，不能混用三者。

## 6. 逐腿发送前盘口刷新与未发送状态

2026-11-12 补充：

- 托管钱包和 CLI 在每条腿签名、发送前重新读取该腿 BBO，按最新盘口计算 IOC 保护价；数量仍使用执行计划的差额，预览中间价仍作为滑点基准，不被新盘口覆盖。
- 最新保护价对应的订单名义低于 10 USD，或盘口读取/校验失败时，该腿不发送，回执进入已知未完成状态。
- 浏览器模式在每条腿发送前同样刷新 BBO。若最新保护价与已签名保护价不同，不修改 action、不提交旧签名，停止后续写入并要求重新预览签名。
- 前腿拒绝、部分成交、结果未知或发送前检查停止时，尚未发送的腿使用 `not_sent`；历史页面对旧回执中终态动作的 `prepared` 腿也显示“未发送”。
- 刷新只降低使用旧保护价的概率，不消除 IOC 零成交、部分成交或两腿非原子执行风险，不自动重试或追单。

## 7. 最大滑点与订单数量深度检查（2026-11-19）

2026-11-18 一次 HYPE/BTC 调仓遇到零成交和部分成交，第三次才补齐。旧调仓采用买入 ask+2 tick、卖出 bid−2 tick 的限价，未按整笔数量检查深度。本轮只改 `adjust`、`adjust-prepare`、`adjust-submit` 及对应 Web 调仓流程；旧测试网 `pair open/close` 沿用原策略，不新增自动补单或反向补偿。

### 7.1 定价与深度

- CLI 参数 `--max-slippage-bps`、Web 整数参数 `max_slippage_bps` 默认 5，即 0.05%，允许 1–50；页面提供 0.02%、0.05%、0.10%、0.20%、0.50%。零、超限值、布尔及小数均拒绝。
- 买单上限为每腿计划中间价 × (1+bps/10000)，卖单下限为中间价 × (1−bps/10000)。价格按合法 tick 向保护范围内取整，不能因取整突破上限。
- 计划生成时读取 L2 盘口，按实际差额数量逐档消耗买单 asks 或卖单 bids，累计限价内可见数量、预计均价和预计最差成交价。可见数量不足则拒绝整个计划，返回所需量、可见量及保护价；不自动缩量或扩大滑点。
- 合约身份必须一致，价格与数量必须为正，档位顺序合法且不得交叉。深度快照最多允许 5 秒陈旧、1 秒时钟超前，异常或过期不下单。
- 差额不足最低下单名义的腿仍跳过；未选择的腿保持原样。只有实际需要下单的腿进行数量深度检查。

### 7.2 发送与签名

预览、浏览器签名准备和托管执行都会生成计划。**托管执行会重新读仓位与盘口生成执行计划，中间价基准可能不同于页面预览**；最大滑点应用于该执行计划，报告保留实际基准。逐腿发送时保护价固定，不随行情扩大。

每腿签名或发送前重新读取完整盘口，按同一保护价和数量复核深度。第二腿深度不足时保留第一腿成交结果，第二腿标记未发送，返回已知未完成；失败腿清除旧的通过快照，不自动撤回第一腿。

浏览器保留已签名限价，在该限价内检查深度。目标金额、腿选择或最大滑点与待签名动作不一致时拒绝。托管 `request_id` 参数哈希加入最大滑点，同一请求不能改用更宽上限继续执行。

### 7.3 展示与兼容

报告新增 `max_slippage_bps`；需要下单的腿新增 `depth`，包含 `book_time_ms`、`required_qty`、`available_qty`、`estimated_avg_px`、`worst_fill_px`。页面显示限价内可见量、预计均价及检查时间，属于快照估算，不是成交承诺。

弹窗仍每 5 秒读取只读 BBO；过期判断改为买单 ask 超过保护价，或卖单 bid 低于保护价。微小价格变化不再使预览自动失效，整笔深度在执行器中重新核对。修改滑点会清除报告和确认金额，要求重新预览。

新 Web 必须搭配新 CLI；执行器未回显相同最大滑点时拒绝结果，不能把旧两 tick 策略包装成新策略。历史报告保留可读，升级前的待签名动作及托管预览须重新生成；不需要数据库迁移。已有未知状态不会因升级自动恢复。

离线验证覆盖买卖多档与 VWAP、边界数量、限价外流动性排除、tick 取整、非法和过期盘口、计划失败零下单、逐腿深度变化、部分成交处理、签名参数变化、托管幂等及桌面/手机控件。IOC 仍可能受行情变化影响；部署、重启和真实下单仍需用户明确授权。

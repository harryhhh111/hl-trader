## 1. 交互模型(全部)

| 命令 | 作用 | 写操作 |
|---|---|---|
| `hl-trader open [--notional <usd>] [--execute]` | 开 pair:多 HYPE 永续 + 空 BTC 永续,等名义 | 默认 dry-run,加 --execute 才下单 |
| `hl-trader close [--execute]` | 关掉整个 pair(反向平掉两腿) | 同上 |
| `hl-trader status` | 看板:仓位 + 资金费 + 动态 | 否,随时可跑 |

第一阶段已有的 `market`、`account`、`order`、`cancel` 原样保留。`status --cloid <id> [--address <address>]` 继续查单,不带 `--cloid` 时显示看板;不存在独立的 `cloid` 或 `positions` 命令。日常使用仍只有上面三个命令。

## 2. open

- **两腿**:多 HYPE 永续 + 空 BTC 永续,目标等名义 1:1。`--notional` 表示每腿 USD 名义;每腿目标 = min(参数或配置金额, 配置比例×权益),比例默认 0.7、只能调小。预览同时显示请求值和限额后的值,仍遵守现有单笔名义上限。权益、金额必须为正数。
- **开仓前检查**:账户任一 BTC/HYPE 持仓、挂单或未解决的动作存在时拒绝新开仓,不能只检查完整 pair。首版沿用独立测试账户和标准永续市场边界,检查两腿均为全仓保证金模式,不自动修改模式或杠杆。例外:市场元数据声明 `onlyIsolated`(交易所层面禁止全仓,实测如测试网 HYPE `strictIsolated`,交易所拒绝 "Cross margin is not allowed for this asset")时,接受该腿逐仓(isolated)并打印警告,自担单腿独立强平风险;主网 HYPE 无此限制,仍要求全仓。
- **taker 执行**:使用 IOC 限价单,买单保护价 = ask+2tick,卖单 = bid−2tick;tick 来自市场元数据,保护价必须满足精度要求。目标是立即吃单,但不保证全部成交;保护价内未成交部分撤销。缺盘口或无法确定合法保护价时拒绝发送。
- **数量与名义**:按市价计算目标数量并向下截断,再用保护价核对单腿名义上限,必要时继续向下减量;零数量或低于交易所最小下单金额时拒绝。精度与实际成交价可能造成两腿名义不完全相等,预览和回执均显示偏差,不自动补量。
- **顺序执行**:先 HYPE 多腿,确认全部成交后再提交 BTC 空腿。两笔交易不具有原子性,按下表处理异常。

| 已确认的结果 | 后续动作 |
|---|---|
| 第一腿拒绝或零成交且订单已终结 | 不发送第二腿,报告开仓失败 |
| 第一腿部分成交且订单已终结 | 不发送第二腿,只减仓撤回第一腿已确认成交量 |
| 第一腿全部成交,第二腿拒绝或终结时未全部成交 | 核对两腿实际持仓,只减仓撤回本次动作已确认建立的仓位,包括第二腿的部分成交 |
| 任一写请求超时、断线或响应无法识别 | 标记结果未知,停止后续写操作;先按 cloid、成交记录和持仓核对,不因超时直接反向下单 |
| 撤回操作拒绝或终结时仍有剩余持仓 | 保留记录并报告剩余敞口,退出码 1;不循环补单 |
| 撤回操作结果未知 | 保留记录,退出码 3,停止后续写操作 |

撤回仅针对当前动作,使用新 cloid 和 `reduce-only` IOC,每腿最多发送一次。它是有记录的补偿动作,不是原写请求重试;即使全部撤回成功,原开仓也应报告失败。遇到结果未知后,本次调用只允许只读核对并返回 3,不自动恢复写操作。单次查单返回“未找到”不能证明未成交,须结合成交、挂单及持仓核对;证据不足时维持未知。

## 3. close

- 按**账户实际持仓**关闭 HYPE 多仓和 BTC 空仓,也允许处理仅剩一腿的情况。以 pair-state 辅助核对;状态文件丢失时,仅在独立账户、方向符合且无未解决订单的条件下重建恢复意图。发现反向持仓或无法解释的账户变化时拒绝写入,明确报告冲突,不猜测仓位归属。
- 两腿使用 `reduce-only` IOC + 保护带,下单前重新核对剩余数量。已成功平掉的一腿不再打开。某腿明确拒绝或终结后部分成交时,可继续关闭另一腿;某腿结果未知时停止后续写操作。每腿每次调用至多提交一次,不自动追单。
- 仅当两腿实际持仓均为零且本次订单均已确认终结时报告成功。已知残仓返回 1,结果未知返回 3;保留恢复记录,用户核对后可再次显式执行 `close --execute`,按最新残仓创建新动作。
- 输出实际成交名义、实现盈亏、手续费和资金费净收支。实现盈亏与手续费来自账户成交记录,资金费来自账户实际收付;按本次 pair 的订单及持有区间归集。数据缺失或状态文件丢失导致无法完整归集时显示“不可完整核算”,不填零、不编造成交。交易平仓结果与核算数据完整性分别展示。
- 完成后将状态标记为 `closed`,保留历史动作与订单回执;下次开仓前归档旧状态,不直接删除审计记录。

### 3.1 动作记录与恢复(open/close 共用)

- 状态位于配置的 `receipt_dir` 下(默认 `.hl-trader/pair-state.json`),目录 0700、文件 0600。第一次发送前持久化账户、网络、动作 ID、两腿意图与 cloid、起始持仓;每次补偿前也先记录独立 cloid。禁止仅在成交后写状态。
- 记录 `prepared`、`opening`、`open`、`closing`、`compensating`、`incomplete`、`unknown`、`closed` 或 `failed` 等阶段,逐笔保存发送前状态、交易所结果和已确认成交量。状态更新采用临时文件、同步、原子替换及目录同步;落盘失败即停止后续写操作,同时保留并输出已知交易所结果。
- 写动作加进程互斥,同一 agent 的 `open/close/order/cancel` 不得并发签名发送;订单 cloid 防重复机制继续保留。锁不能因“回执存在”而被删除。进程退出后重新读取记录并向交易所核对,不凭本地记录认定成交或重发。
- `status` 只读展示未完成动作、实际持仓和核对结果,不修改状态、不恢复交易。后续显式 `close --execute` 必须先解决已有订单的未知状态并记录核对结果;若仍无法确认终结,或挂单尚未处理,拒绝新增写请求并提示查单/撤指定单。`open` 只在旧动作已核清、无持仓和挂单时开始新动作。

## 4. status 看板(只读,三块)

以下为展示模板,占位值不代表实时行情或已核实事件:

```text
== 仓位 ==  权益 1087 USDC
  HYPE 多  <数量> (当前名义 <USD>, entry <价格>, 名义/权益 <倍数>, uPNL <金额>)
  BTC  空  <数量> (当前名义 <USD>, entry <价格>, 名义/权益 <倍数>, uPNL <金额>)
  名义比 <HYPE/BTC> (漂移 <百分比>); 未完成动作 <无/阶段及 ID>

== 资金费 ==  (每小时结算,按费率正负判断收付)
  HYPE 当前 <每小时费率> (简单年化 <百分比>)  BTC 当前 <每小时费率> (简单年化 <百分比>)
  按当前费率和持仓不变预估:日净收/付 <USDC>
  近 3 次账户实际收付:<时间、币种、金额; 无数据时明确说明>

== 动态 ==
  解锁锚点:<已核实来源及日期/未配置>; 实际申领动态:<已核实信息/未核实>
  HYPE/BTC: <比价>, 30MA 上/下方 <百分比>
  官方动态:[可机器获取则列出,否则明示"请人工查看官方 X @HyperliquidX"]
```

- 行情及账户数据来自 Hyperliquid 测试网 info 端点:`metaAndAssetCtxs` 提供当前 funding、markPx 和 oraclePx;`fundingHistory` 是市场历史费率,账户真实收付应使用 `userFunding`;`userFills`/`userFillsByTime` 提供成交、手续费及已实现盈亏。需要时分页、去重,不把截断数据当成完整历史。
- Hyperliquid 每小时结算。正费率多方付空方,负费率相反;pair 净收付须合并两腿。以小时费率 `r` 计算简单年化 `r×24×365`;预计小时净收入为 `−Σ(有符号持仓数量×oraclePx×r)`,日预估再乘 24。明确这是当前费率不变的估算,不代表未来实际收付;持仓名义展示使用 markPx。
- 用 `candleSnapshot` 分别取 HYPE、BTC 的日线,按相同 UTC 日期对齐,计算已收盘日的收盘价比值及最近 30 日均值。缺数据时显示不可用,不补零;仅展示均线位置,不从单一均线推断未定义的 overlay 策略状态。名义比按绝对名义计算,分母为零时显示无仓或单腿敞口。
- 解锁日历来自人工配置的已核实公开来源,记录来源链接和核实日期,7 天内的锚点才提醒。日历不能证明实际申领发生或没有发生;未核实的日期、数量与 announced claim 动态明确显示“未核实”,不写死未经确认的 cliff 示例。
- 官方动态:实现时探测官网/文档的机器可读更新源;拿不到就**明确标注**,不静默、不编造。
- 看板每次运行实时拉取,显示网络与数据时间,单块失败时标注不可用并保留其他结果;不保存日报、无 daemon。交易状态与回执仍按 §3.1 持久化。

## 5. v1 有、v2 明确砍掉的东西

- **自动再平衡(cron/rebalance 命令)**:两腿名义随价格漂移,status 显示漂移%,由人决定是否 `close` 后重新 `open`。若四笔交易每笔名义均为权益的 `f`,每笔 taker 费率为 `r`,完整往返手续费/权益约为 `4×f×r`;仅以 `f=0.7`、`r=0.045%` 举例,结果是 `0.126%`,不是固定 `0.09%`。费率只是算例,以实际账户和市场为准;真实成本按各笔成交名义与费率求和,另计滑点及持有期资金费。
- **自动熔断**:人盯 status,异常自己 close。
- **intel collect 日报文件、~/.hl-trader/intel/ 目录、自动写 stock-research**。
- pair 子命令组(plan-open/rebalance 等),改为顶层三个动词。

## 6. 不变的第一阶段纪律

dry-run 默认,可进行只读查询和预览,不加载私钥、不签名、不创建或修改交易状态;写操作显式 --execute。写请求禁止自动重试;超时=结果未知;秘密不进聊天/仓库/日志;主网这一步不做(上线需另行书面授权)。

4. 新增 `src/intel.rs`:区分市场费率与账户收付、小时年化和净收付计算、HYPE/BTC 30MA、可追溯的解锁锚点、官方动态探测;渲染三块 status 并兼容 `status --cloid`。
5. 扩展 mock 测试:第一/第二腿拒绝、零成交与部分成交;超时但交易所实际成交时不盲目补偿;补偿残仓/未知;close 不反向开仓且只减仓;未知订单未核清时阻止后续写入;进程在两腿之间中断后的恢复;回执写入失败;重复动作与并发写互斥;精度截断/保护价上限/最小金额;已有单腿或挂单拒绝开仓;费率正负、小时年化、历史收付和缺失数据;旧查单命令兼容。默认并行 `cargo test`、`cargo clippy --all-targets -- -D warnings`、`cargo fmt --check` 全部通过。
6. 报告后请用户授权测试网联调:`open` 建 pair → `status` 核对读数 → `close` 平仓归零。

## 8. 风险与已知限制(如实写进 README)

- 无自动再平衡:单边行情漂移可能持续扩大,极端时 pair 退化近似单腿敞口,靠人看 status 发现。
- 测试网验证不了主网的真实滑点、流动性和资金费水平;看板显著标注测试网。资金费净收付由当时两腿持仓和费率共同决定。
- 两腿及补偿均非原子操作,可能留下已知残仓或结果未知;本工具不承诺自动恢复为无敞口状态。独立账户若同时被外部程序或人工交易,动作归属可能无法判定,此时停止写入。
- 边缘衰减:原方案引用的 +90.8%/年是历史回测口径,本次未复核其数据与算法,不作为验收目标或未来收益承诺;status 仅提供观测信息。
